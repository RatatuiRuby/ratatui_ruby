# The TERMINAL Mutex: History, Bug, and Resolution

> **Status**: Bug documented. Fix in progress.  
> **Date Discovered**: 2026-01-23  
> **Discovered Via**: Rooibos app freeze when calling `viewport_area` inside View

---

## Executive Summary

The global `TERMINAL: Mutex<Option<TerminalWrapper>>` in `terminal.rs` causes **deadlock** when any terminal-querying function (like `viewport_area`) is called from inside a `draw()` callback block.

This is a fundamental design flaw, not a bug in usage. The Mutex was introduced by an AI (JetBrains Junie) as a cookbook pattern for "mutable global state in Rust" without consideration for callback reentrancy.

**Recommended fix**: Trait-based query interface with compiler-enforced snapshot pattern. See [The Fix](#the-fix).

---

## The Bug

### Symptoms

When a Rooibos app calls `tui.viewport_area` inside the View lambda, the app **freezes forever**:

```ruby
View = -> (model, tui) {
  width = tui.viewport_area.width  # 💀 DEADLOCK
  # ...
}
```

Ruby's `Timeout` cannot interrupt the freeze because the thread is blocked on a kernel futex, not executing Ruby code.

### Root Cause

```
draw() 
  → TERMINAL.lock()         # Lock acquired
    → yield to Ruby block
      → View lambda executes
        → tui.viewport_area
          → _get_terminal_area (FFI)
            → TERMINAL.lock()  # 💀 DEADLOCK - already held!
```

`std::sync::Mutex` is **not reentrant**. When the same thread tries to lock a Mutex it already holds, it blocks forever.

### Affected Functions

Any Rust function that acquires `TERMINAL.lock()` will deadlock if called from inside `draw()`:

| Function | File | Deadlock Risk |
|----------|------|---------------|
| `get_terminal_area` | terminal.rs | Query during draw |
| `get_terminal_size` | terminal.rs | Query during draw |
| `get_viewport_type` | terminal.rs | Query during draw |
| `get_cursor_position` | terminal.rs | Query during draw |
| `get_cell_at` | terminal.rs | Query during draw |
| `poll_event` | events.rs | Test mode check |
| `insert_before` | terminal.rs | Write operation |
| `set_cursor_position` | terminal.rs | Write operation |
| `resize_terminal` | terminal.rs | Write operation |

> [!WARNING]
> **`poll_event` is an additional deadlock vector.** It checks if the terminal is in test mode by acquiring `TERMINAL.lock()`. If a Ruby callback inside `draw()` ever polls for events, deadlock occurs.

### Full Audit of Mutex Statics

The codebase contains 5 distinct `Mutex`-protected statics:

| Static | Location | Lock Sites | Callback Risk |
|--------|----------|------------|---------------|
| `TERMINAL` | terminal.rs:23 | 16 (terminal.rs) + 1 (lib.rs) + 1 (events.rs) | **YES** |
| `IS_FULLSCREEN` | terminal.rs:25 | 2 | No |
| `TERMINAL_INSTANCES` | terminal.rs:29 | 3 | No |
| `EVENT_QUEUE` | events.rs:7 | 3 | No |
| `LAST_PANIC` | lib.rs:123 | 2 | No |

Only `TERMINAL` has callback reentrancy risk because only `TERMINAL` is held across a `yield` to Ruby code.

## History: Why the Mutex Exists

### Origin: Proof of Concept (2025-12-22)

Commit `b822b44` "Proof of concept" introduced the pattern:

```rust
lazy_static::lazy_static! {
    static ref TERMINAL: Mutex<Option<Terminal<CrosstermBackend<io::Stdout>>>> = Mutex::new(None);
}
```

This commit was **generated by JetBrains Junie** (an AI coding assistant):

```
commit b822b44d6944758bebb53aff5843479f44baf1d8
Author: Kerrick Long <me@kerricklong.com>
Date:   Mon Dec 22 01:27:17 2025 -0600

    Proof of concept
    
    Generated with [JetBrains Junie](https://www.jetbrains.com/ai/)
    
    Co-Authored-By: Junie <junie@jetbrains.com>
```

### Why Junie Chose Mutex

Rust requires synchronization primitives for mutable static data. The options are:

1. `static mut` + `unsafe` - Forbidden without unsafe blocks
2. `lazy_static! + Mutex` - The "safe" cookbook pattern
3. `thread_local! + RefCell` - For single-threaded scenarios
4. `OnceCell` / `OnceLock` - For write-once data

Junie chose option 2 because:
- It's the default pattern in Rust tutorials
- It compiles without `unsafe`
- It works for a proof of concept

**There was no deliberate threading consideration.** The AI was solving "Rust won't let me have a mutable global" not "I need to protect this from concurrent access."

### Evolution of the Pattern

| Commit | Date | Change |
|--------|------|--------|
| `b822b44` | 2025-12-22 | Initial `lazy_static! + Mutex` |
| `db19556` | 2025-12-22 | Extracted to `terminal.rs` |
| `988a66f` | 2025-12-29 | Changed to `const` initialized Mutex (removed lazy_static for TERMINAL) |
| `5a4cbda` | 2026-01-XX | Added `TERMINAL_INSTANCES` HashMap with lazy_static |

The pattern was never questioned because it "worked" for all use cases until Rooibos Views needed to query terminal state inside draw callbacks.

## Why Mutex is Wrong for This Use Case

### Ruby's GVL (Global VM Lock)

Ruby 3.x uses a Global VM Lock (historically called GIL). Only one thread executes Ruby code at a time. All Rust FFI calls from Ruby are therefore serialized.

This means:
- `TERMINAL` is only ever accessed by one thread at a time
- Thread-safety primitives are **unnecessary overhead**
- Reentrancy (same thread, nested calls) is the actual concern

### What We Thought Might Be the Correct Primitive

For single-threaded scenarios with reentrancy needs, Rust provides:

```rust
thread_local! {
    static TERMINAL: RefCell<Option<TerminalWrapper>> = RefCell::new(None);
}
```

Benefits:
- **No locks** - Zero synchronization overhead
- **Clear errors** - `RefCell` panics on overlapping borrows (debug-friendly)
- **Future-proof** - Each Ractor would get its own terminal (if Ruby Ractors ever matter)

### Why Simple RefCell Won't Work

Initial analysis suggested `thread_local! + RefCell`. However, this only prevents deadlock—it causes panic instead. The deeper problem is that during `terminal.draw()`, ratatui holds `&mut terminal`, and **Rust's aliasing rules prevent any other reference** (even `&self` for read operations).

## The Fix

### Architecture: Compiler-Enforced TerminalQuery Trait

All queries route through a `TerminalQuery` trait with two implementations:

1. **`LiveTerminal`** - Used outside draw, queries the actual terminal
2. **`DrawSnapshot`** - Used during draw, queries a pre-captured snapshot

```rust
pub trait TerminalQuery {
    fn size(&self) -> Rect;
    fn viewport_area(&self) -> Rect;
    fn is_test_mode(&self) -> bool;
    fn cursor_position(&self) -> Option<(u16, u16)>;
    fn cell_at(&self, x: u16, y: u16) -> Option<Cell>;
}

struct LiveTerminal<'a>(&'a mut TerminalWrapper);
impl TerminalQuery for LiveTerminal<'_> { ... }

struct DrawSnapshot { size: Rect, viewport: Rect, buffer: Buffer, ... }
impl TerminalQuery for DrawSnapshot { ... }
```

### Why This Can't Be Forgotten

When adding a new query:

1. Add method to `TerminalQuery` trait
2. **Compiler error**: `LiveTerminal` doesn't implement new method
3. **Compiler error**: `DrawSnapshot` doesn't implement new method
4. Developer **MUST** implement both or code won't compile

### Storage Architecture

```rust
thread_local! {
    static TERMINAL: RefCell<Option<TerminalWrapper>> = RefCell::new(None);
    static DRAW_SNAPSHOT: RefCell<Option<DrawSnapshot>> = RefCell::new(None);
}

/// Queries route here. Returns snapshot during draw, live terminal outside.
pub fn with_query<R>(f: impl FnOnce(&dyn TerminalQuery) -> R) -> Option<R>;

/// Mutable access. Only works OUTSIDE draw.
pub fn with_terminal_mut<R>(f: impl FnOnce(&mut TerminalWrapper) -> R) -> Option<R>;

/// Draw execution. Captures snapshot BEFORE calling terminal.draw().
pub fn lend_for_draw<R>(f: impl FnOnce(&mut TerminalWrapper) -> R) -> Option<R>;
```

### Behavior Matrix

| Operation | Outside Draw | During Draw |
|-----------|--------------|-------------|
| Queries (`viewport_area`, `size`, etc.) | ✅ Live terminal | ✅ From snapshot |
| Write ops (`insert_before`, etc.) | ✅ Live terminal | ❌ `Error::Invariant` |

### Migrating All Mutex Statics

While only `TERMINAL` has callback reentrancy risk, **all 5** mutex statics will be migrated to `thread_local!` for safety. Mutexes can silently deadlock; RefCell/Cell panic with a stack trace.

| Static | Migrate To | Reason |
|--------|------------|--------|
| `TERMINAL` | `RefCell` + TerminalQuery trait | Complex callback pattern |
| `IS_FULLSCREEN` | `Cell<bool>` | Simple flag, no callback risk |
| `TERMINAL_INSTANCES` | `RefCell<HashMap<...>>` | No callback risk |
| `EVENT_QUEUE` | `RefCell<VecDeque<...>>` | No callback risk |
| `LAST_PANIC` | `RefCell<Option<String>>` | No callback risk |

## Expert Perspectives

During debugging, multiple "expert hat" perspectives were considered:

| Perspective | Recommendation |
|-------------|----------------|
| **Senior Architect** | Thread-local (clean decoupling) |
| **Concurrency Expert** | Thread-local (avoid reentrant lock smell) |
| **Rust Core Team** | `Cell`/`RefCell` (no locks for single-thread) |
| **Performance** | Thread-local (~2-5ns TLS vs ~10-20ns Mutex) |
| **Ruby Core Team** | Thread-local (invisible to Ruby, clean API) |
| **Magnus Maintainer** | `thread_local! + RefCell` (single-threaded FFI) |
| **OS Engineer** | Thread-local (kernel pattern, futex-free) |

**Unanimous consensus**: Thread-local with `RefCell` is the correct primitive for storage. The additional TerminalQuery trait pattern handles the callback reentrancy that simple RefCell cannot.
